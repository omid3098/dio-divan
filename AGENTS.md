# Project instructions

- **What and where.** Dio Divan runs flows of AI coding-agent harnesses (Claude Code, Codex, Grok, Pi, and Windows-only Hermes; agy is manual-only and uncontrolled), saved as Divan models. A council is one flow: members answer one question independently and blind; a chairman weighs their full reports and JSON summaries (or a kept prose report), scores them and writes one answer as long as the question needs. A design can wire the agents differently; Omid then comments or presses «دور بعد بدون نظر». Every round is a node in a branching tree shown in a web editor. `src/shared` (types, the context builder, defaults, text helpers: used by the server and the web editor), `src/server` (Node `http` + SSE, the one flow/round engine, the Library resolver, the harness adapters in `src/server/adapters`, storage), `web/` (React + Vite + React Flow + dagre; Persian, right to left), `schemas/` (the member, chairman, report and lens-planner JSON Schemas), `pi-extension/` (the `/divan` command and the `divan` provider: the Divan profiles as models in Pi; the models are listed from `settings.json` at Pi's startup WITHOUT starting Divan, and Divan is started by the first real use: `/divan`, or the first prompt to a divan model, in a `before_agent_start` hook that Pi awaits, with `before_provider_request` as the net; **the extension never writes in Divan's home: the server alone makes the home and the API key (an exclusive create under its lock, owner-only before the secret is written, a loser rereads the winner's key), so two Pi instances starting at once cannot race it; the extension reads the key once the server is up and registers the provider again with it (a provider can be registered again and takes effect at once; until then it holds a placeholder no server accepts); the key is remembered as registered only once Pi has taken the registration, so a failed one is tried again by the next use, and a server that is up with no usable key is an error that says so**; **it starts Divan through the launcher, not as its own child: it spawns `divan start --no-wait --port N` (detached, in the user's home folder with an absolute `DIVAN_HOME`, so that neither the launcher nor the server keeps Pi's folder as its working directory), which starts the server detached and exits at once, so the server is in nobody's process tree when T3 Code kills Pi's whole tree; the environment it passes has `T3_ACP_*` and `ELECTRON_RUN_AS_NODE` taken out, and it takes a server for Divan only when `/api/health` answers the pid that `server.json` names (see the T3 Code bullet below)**; the extension keeps copies of `DEFAULT_PORT`, of `PI_THINKING_LEVEL_MAP` and of the environment rule so that its folder stands alone, and `tests/pi-extension.test.ts` asserts that the first two are the same), `e2e/`, `brand/` (Divan's own mark, the seal: its SVG, PNG and `.ico` files and a short usage guide in `brand/README.md`; Dio Docs' «Divan's seal» page owns its rules) and `scripts/brand.mjs` (the seal's ONE geometry: it writes `brand/`, the browser tab's `web/public/favicon.svg` and `web/src/components/divan-mark-paths.ts`, which `DivanMark` in `web/src/components/divan-mark.tsx` draws in the theme's glow colours, the small cut below 32 px; none of those outputs is edited by hand). `src/server/engine.ts` imports no HTTP or web code: another front end can call `Engine` and listen to its events. - **Divan flows (Omid, 2026-10-13; built work approved that day).** ONE `Engine.execute` (`src/server/engine.ts`) runs the validated directed acyclic graph (DAG: steps joined one way, with no loops); a council compiles into the same flow (`compileCouncil`, `src/shared/flow.ts`), never a second engine. `Flow.version` is 1, `kind` is `council` or `custom`; nodes are `input`, `agent`, `condition`, `output`. `validateFlow` runs before admission: one input and output, 3–18 nodes, at most 80 edges, stable unique ids of 1–32 letters, digits, `_` or `-`, no dangling/duplicate connections, cycles, unreachable boxes or dead ends, valid forms/access/dependencies, possible minima, no disabled required prerequisite or disabled final. Agent rules and serialized schema are each at most 64000 characters. `orderedNodes` gives deterministic topological order; the pure `scheduleFlow` chooses ready agents, code-only conditions, blocked and branch-skipped steps. Independent ready agents run concurrently as a wave (`Promise.allSettled`); the wave settles and its queued checkpoint must save before any dependent call starts. Admission, cancellation, one active round per session, mutation order, retries, watchdog, revisions, tombstones and save-before-done stay in `Engine`.
  - *One stored execution.* A new session is `schemaVersion: 2`; its resolved `SessionSettings.flow` freezes every agent's rules, schema, access, form display metadata and level. A new round keeps `ChairNode` as its tree envelope (id, parent, `kind: 'chair'`, final answer fields, usage and cumulative `attempts`), with ONE `steps: FlowStep[]`: stable id, form, run state, exact prompt/input, parsed/sanitised output, times, activity, aliases, upstream `inputs` and attempt indices; condition steps also keep source, result and reason. Steps are not nodes of the conversation tree. No second writable `seats`/`chairman` copy is saved. Version-1 sessions still load, using their stored rules/schemas; `seatsOf`, `runsOf`, `chairmanOf`, `stepOf` and `replaceChairman` are the compatibility selectors in `src/shared/flow.ts`, with ephemeral report/custom member views for the old panel. Load does not rewrite all old sessions into today's defaults.
  - *What a node sees (Omid, 2026-10-13).* In a design wires alone choose the current-round outputs an agent gets, and the answer is the one from the agent wired to output. The conversation context is sent to EVERY agent automatically, once (`buildContext`, `src/shared/context.ts`): the root question/context, user inputs on this path, earlier answers' titles/directions, the full latest answer/claims/questions, and the new input or critique instruction; never a sibling conversation branch or historical member reports. Wires add only connected, validated sanitised payloads, JSON in code-made anonymous, nonce-delimited, defused blocks (`upstreamInput`, `projectOutput`, `src/server/prompts.ts` / `src/shared/flow.ts`); generated output never becomes a system rule. Aliases are made per recipient, not editor names or model ids. «Members never see each other» is the SHAPE of a council (no member-to-member wire), not a restriction on designs: a critic can read the wired draft. Roles (`member`, `writer`, `critic`, `chairman`, `rewriter`) restrict neither forms nor prompts and add no hidden task text.
  - *Required inputs and one response group.* An agent declares `required: string[]` and at most one `responses: {ids, min}`; every incoming agent data wire is declared once in one of them. Context/input never counts toward the minimum. All required inputs must succeed; all response peers must settle before the minimum is checked. The council final needs two valid members; a writer/critics rewriter needs its writer AND two valid critics (the draft is never another vote). A failed/impossible dependency becomes `blocked`, never pending forever. One final answer producer has ONE edge to output, the built-in `answer` form, enabled and web off; other agents may also use an answer form, but they do not give the output. Alternative branches join into the final agent through a response group (minimum 1 for alternatives), as Astra's review prescribed and Omid accepted on 2026-10-13; zero successful branch responses fails. `finalInputsReady` governs stop-rest: resolved active gates, every required input valid and the final's own response minimum met, not a hard-coded two for designs.
  - *Conditions, gates and field picks (accepted Astra review, 2026-10-13).* A condition has one data input from a non-report agent; 1–30 rules over its top-level fields, `mode: all|any`, type-checked operators and values (`validateCondition`, `evaluateCondition`). Number comparisons, text empty/contains/equals, boolean true/false, choice is/is-not, list empty/count comparisons are code, no harness call. Both `yes` and `no` exits must be used, by a gate or by a line tied to that exit (below); a gate carries NO payload and can lead to an agent or condition. No gates means active; otherwise wait for ALL gates to settle and activate if ANY is active, branch-skip if all are inactive (`gateState`). An inactive condition skips both exits. An active condition with failed/user-skipped source goes to no; a missing/null referenced field makes the WHOLE condition false, even in `any`. Interruption is recovery, not no. A branch-skipped required input propagates branch-skipped; failed, unavailable or user-skipped required input blocks. Response minima never shrink: below minimum, skip only when every peer is branch-skipped, otherwise block. A fallback must have its own data wires, not require a failed producer. A data wire's optional `fields` is a nonempty, unique selection of top-level source fields; absent means all. No field picks from report, input or gate, or into a condition; picks grant only that payload, never raw text or diagnostics. `maxCalls` counts enabled agent nodes, including the final, excluding conditions and retries: the displayed upper bound on calls per round, not tokens; an inactive branch lowers actual calls. Loops remain for later.
  - *Lines tied to an exit (Omid, 2026-10-13, after the first real test needed a pass-through agent; built from Astra's REVIEW-3, approved that day).* An agent-to-agent data wire may carry `when: {condition, exit}` (`yes` or `no`): it delivers only when that condition took that exit, so a branch can carry an earlier answer straight to the final agent. Only agent→agent data wires take it, naming a condition node and a valid exit; it counts as a use of that exit in `validateCondition`, its implied condition→recipient link is part of cycle detection, reachability and `orderedNodes`, and `canonicalFlow` covers it (absent means always); `maxCalls` is unchanged. `wireState` (`src/shared/flow.ts`) derives `active`, `inactive` or `waiting` per recipient, never stored. A recipient waits until every incoming `when` resolves, even with an active OR gate; an inactive wire is settled branch absence whatever its producer did; an inactive required wire branch-skips the recipient; a response group counts only active successful payloads against its unchanged minimum. A skipped condition activates neither exit; a failed or interrupted one is unresolved recovery, never «no». Payloads and `step.inputs` are filtered by wire state before field projection; `Engine.skipUnavailable` marks availability only after branch absence is settled (all-inactive response groups too), so an inactive fallback never becomes `unavailable`. Recovery: `invalidateDescendants` follows the condition→recipient links; a rerun first invalidates the decisions its planned retries affect, then recomputes the needed producers, so one retry suffices when the decision flips (code review 4). Withholding: an unresolved wire grants nothing, after the decision only active wires grant access, and undecided recipients stay possible readers. `eligibleFlow` enumerates recipient-specific wire states and `finalInputsReady` requires every incoming decision resolved, required wires active and successful, and enough active responses. The edge inspector's «Only when» (Always, or a condition's Yes/No) sets it; the canvas labels the line «only if Yes»/«only if No».
  - *Withholding, recovery and retry.* `releasableSteps` considers every pending/running agent that may still run, unresolved branches included; it excludes only definitely inactive readers. A payload can be checkpointed only if EVERY remaining reader has a data wire authorising all its fields; gates grant nothing and partial field access withholds the whole payload. `serializeSession` (`src/server/store.ts`) applies it on EVERY save (progress, rename, layout too): with unresolved work, raw output, prompts containing upstream material, parsed copies, diagnostics and tool logs stay withheld; only authorised sanitised output and its activity counts may be released. Conditions save provenance/results, no source payload copy. Settle conditions/skips before dependent calls/checkpoints. A writer's draft can survive the critic wave, while critic replies cannot be saved for another critic to read. `interruptRunning` retains safe durable outputs and attempt costs; lost RAM-only answers and in-flight work become interrupted. `invalidateDescendants` clears downstream outputs, conditions and previously skipped branches when a source was lost or is rerun. `Engine.rerun` reuses valid durable steps with unchanged inputs and sufficient response groups; needed availability/user skips are retryable, inactive/disabled branches stay distinct. It must save the new withholding state successfully BEFORE restarting calls. RAM-only success cannot survive a crash.
- **Profiles hold flows (approved 2026-10-13).** `ProfileRecord.flow` holds a custom `StoredFlow` in settings version 2: Library references (`prompt`, `form`), no copied rules/schema/formInfo (`storedFlow` strips them even if supplied). Council profiles keep their base seats/chairman and compile only after level resolution, preserving Low pruning. `resolveLevel` in `src/server/settings.ts` is still the ONE resolver: `deriveLevel` applies `effortForLevel` to each design agent, then `levels[level].nodes[id]` overrides its enabled/harness/model/effort; changing a model/harness without an effort derives that model's level effort. A design keeps all its steps at Low and only lowers efforts; no required writer, final or condition is pruned. Council levels still use seat/chairman overrides and switch the slowest member off at Low when more than three would run. Resolve the base and all derived/effective levels against ONE Library/settings snapshot, after overrides, before validation, `flowCouncil`, eligibility and fingerprints; invalid stored references block only that model/level (`flow_invalid {reason}`), not settings load.
  - *Every entrance runs the same snapshot.* Web, `/v1` and ACP thread starts consume the resolved flow; sessions, forks in that session and reruns keep the frozen flow. `canonicalFlow` sorts executable graph structure/object keys and covers rules, schemas, custom local fields/limits, model/effort/access/enabled state, required/group ids/minimum, conditions, gates, anonymity and field picks; it excludes canvas positions, editor labels and form display names. `Gateway.identityOf` hashes the actual new or frozen execution plus availability and budgets, profile id/generation, level (and session id for a frozen continuation), with the existing conversation/folder identity BEFORE cache lookup or in-flight sharing. Custom graphs use the execution hash rather than a revision changed by canvas-only saves; compiled councils retain profile revision. A Library edit therefore changes execution identity, and cannot borrow cached answers or live work from old text/schema. `eligibleFlow` (`src/server/eligibility.ts`) applies `eligibleSeats`/`outFor` to all agents, Quick's family separation only to independent members/critics, and enumerates feasible condition branches: mutually exclusive peers cannot jointly meet a minimum. Admission needs some feasible path to the final; `Engine.skipUnavailable` rechecks active delayed agents before calls, and the scheduler enforces the chosen branch's prerequisites.
  - *Starts and direct answers.* `FLOW_TEMPLATES`, `flowTemplate`, `flowForms`, `executableFlow` and `frozenFlow` live in `src/server/flow-templates.ts`. `POST /api/profiles` accepts `template: council|writer-critics|single`; council keeps the ordinary profile, writer-critics copies writer settings into a SEPARATE rewriter call, single is input → one answer agent → output. There is no hidden shared harness conversation or live writer/rewriter coupling. `isDirectAnswer` means an answer-form agent with no required or response agent inputs; the editor chooses `divan.direct` for that case (or keeps a selected custom prompt). `directAnswerRules` (`src/server/prompts.ts`) reuses checked, first-hand evidence, strongest countercase, read-only reach and memory rules, gives a recommendation only when a decision is asked, follows the question's reply language/register, does not repeat questions already answered and keeps the normal final answer shape with empty scores and null dissent/agreement. Lenses remain FIRST-round preprocessing on compiled councils only; `flow_lenses` refuses them on a custom design.
- **The Library (linked entries, Omid, 2026-10-13; approved that day).** `settings.json.library: {prompts, forms}` stores custom entries only (missing means empty), at most 200 in total. `src/shared/library.ts` owns entries/validation/form compilation; `src/server/library.ts` owns generated built-ins, snapshot resolution and views; `SettingsService.editLibrary` owns the serialized atomic edit. Built-in prompts `divan.member`, `divan.chairman`, `divan.direct`, `divan.report`, `divan.critic` and forms `member`, `answer`, `report` are generated, read-only. Duplicate a prompt to change it; report/custom forms can be duplicated, nested member/answer forms cannot be flattened by the field builder (`builtin_form_not_flat`). The report writer and critic reuse the members' approved working rules: check sources, weigh first-hand results, argue the strongest countercase, use only granted read tools/memory/web, never identify themselves; `CRITIC_TASK` is visible in `divan.critic`, not added by the engine's role. No role adds hidden task text.
  - *Linked, not copied.* Editing an entry changes EVERY model referring to it from then on (Omid, 2026-10-13), while sessions keep exactly the resolved text/schema/form name/fields/revision they started with. - **Every change to a session goes through ONE queue per session (`Engine.mutate`).** Layout writes, rename, delete, the admission of a round (and of a session with its first round), a retry, the saves of a round's progress and of its members' answers, and a round's finalization are all one kind of thing: a mutation works out its new state apart from the live session, writes it (`Store.save` with an overlay: nodes, layout, name, time), and only then makes it the session's own and announces it, and it runs to the end before the next one starts. - **Divan as its own provider in T3 Code (ACP; Omid, 2026-10-11/12).** T3 Code has no OpenAI-compatible provider, so Divan is a provider of its own there, through the Agent Client Protocol: in T3's settings an ACP Registry instance with the source «Local command», named Divan, the executable `node.exe` (T3 starts it with `shell: false` and refuses a `.cmd`, `.bat` or `.mjs` as the executable) and the arguments `--disable-warning=ExperimentalWarning <abs>\bin\dio-divan.mjs acp` (`EndpointInfo.acp`; the Connect page shows them).   - *The bridge (`src/server/acp.ts`; imports only `node:*`, `./launch.ts` and `../shared/*`).* Hand-written newline-delimited JSON-RPC 2.0 on stdin and stdout, requests handled concurrently (a `session/prompt` stays open while `session/cancel` arrives). **stdout carries only one-line JSON-RPC messages**: one writer (`send`), `console.log`, `info`, `debug` and `warn` redirected to stderr, because T3 closes the connection at any other line (a blank one too) and at any `session/update` that fails its schema; blank input lines, responses, `$/` messages and notifications it does not know are ignored, an unknown request is -32601, ids are echoed exactly (T3's are numbers such as 4294967296). `initialize` answers protocol version 1 (T3's request is a hybrid of v1 and v2) with NO `info` key, `agentInfo` (`dio-divan`, «Divan»), `loadSession: false`, `sessionCapabilities.resume` and no authentication methods. **The models are Divan's profiles**, one select with `category: "model"`, value `d1-<profile id>` and name `d1-<label>` (`default`, `quick`, then the custom profiles; read from `settings.json` with no server, `profilesFromSettings`; the values `default` and `auto` are never used because T3 never applies them), and the reasoning level is a second select, `effort` with `category: "thought_level"` (Low, Medium, High, Max). `configOptions` is built fresh from `settings.json` every time (a profile made meanwhile is there, and the conversation's own profile always is); `session/set_config_option` answers the whole list; until the user picks a level it follows the profile's own `defaultLevel`. T3 never calls `session/fork`: a fork is a fresh `session/new` whose first prompt starts with `Context handoff (…):`, holds our earlier answers verbatim, and ends `\n\nUser message:\n<text>`. The text after the LAST `User message:` is the message; the last round the handoff names (`lastRound`: the closing links of our answers) is `from`, where the fork continues; and the handoff always goes along as `background`, which the server reads only when that round no longer exists. `Continue where you left off.` (`CONTINUE_TEXT`, `src/shared/acp-text.ts`: the one spelling the bridge and the server share) is T3's «continue» after a stopped run. A round that failed is a JSON-RPC error of the prompt (-32603, with « Open it in Divan: <link>» when there is a link) and the thread stays usable; an error never carries the words T3 reads as a request to sign in (`plain`). `session/cancel` is a notification: it aborts the stream (closing it cancels the round on the server) and answers the prompt AT ONCE, within T3's 10 seconds, with `{stopReason: "cancelled"}`, **exactly once** (`finish`: whichever of the stream's end and the cancel comes first answers, the other is dropped, and no update follows an answer).   - *The server side (`src/server/divan-api.ts` the routes, `src/server/threads.ts` the mapping with no HTTP, `Store.readThreads` and `updateThreads`).* Behind the `/v1` guard (API key, no browser headers; `src/server/server.ts` sends `/v1/divan/` to `handleDivan`): `GET /v1/divan/threads/:id` answers `{id, sessionId, chairId, profileId, level, cwd}` (`chairId` is the thread's tip) or 404 `no_thread`; `POST /v1/divan/threads/:id/turns` takes `{profile, level?, text, cwd?, from?, background?}` (a thread id is 8 to 128 letters, digits, `_` or `-`, else 400 `bad_thread`; `profile` may carry a leading `d1-` or `divan/`; an unknown profile is 404 `model_not_found`, a blocked level 409 `profile_blocked`, an empty text 400 `empty_message`, a bad body 400 `bad_request`, all before the stream starts and in the `/v1` error shape) and answers `application/x-ndjson`, one JSON object a line, a bare `\n` every `KEEPALIVE_MS` (`DIVAN_KEEPALIVE_MS`) through silences of up to ten minutes: `note` (a folder that was not used, a busy session), `round {sessionId, chairId, plan}` once the round is admitted, `plan` whenever the checklist changes, `progress {text}`, and the end, `answer {sessionId, chairId, content, usage: {round, session}}` (`content` is `answerText` and then the closing link, the endpoint bullet above; `round` is the round's `usage.total`, `session` the sum over the session's rounds) or `error {code, message, link}`. - **Lens modes (an experiment; Omid, 2026-10-10).** `POST /api/sessions` takes `lensMode`: `"off"` (the default; absent is the same), `"angle"` or `"only"`; any other value is 400 `bad_lens_mode`. It is kept in `session.settings.lensMode` (absent when off) and is locked with the session. Compiled councils only (`flow_lenses` on a design). API only: no control on Home, nothing in the web UI, not on `/v1`. A lens is a short investigative question made for the asker's question by ONE planner call before the members start (`Engine.planLenses`): on the chairman's harness, model and effort, with no tools, no memory, no folder, and an input of the question as written plus the context text (`plannerRules` / `plannerInput` in `src/server/prompts.ts`; schema `schemas/lens-planner.schema.json`; `parsePlanner`). It returns `{lenses: [{question, why}]}`, at most N (members that take part minus 1 in `angle`, the members in `only`), each question at most 30 words, neutral (it may find nothing), specific, not overlapping; it may return fewer, or none. `angle`: every member answers the whole question and ends its prompt with "Your additional angle: <lens>. Investigate it where relevant. Do not assume its premise, do not force disagreement, and do not neglect the overall recommendation."; the anchor, the first enabled seat of the council among those that take part, has no lens; the others get one lens each at random (`assignLenses`). `only`: no anchor; each member gets one lens at random, and its prompt has the task line of the rules replaced by `onlyTaskLine`: it must NOT answer the question, only the lens, with all the context, and reports (a) a direct finding in `stance`, (b) sources inside its `claims` (and `memory_facts`), (c) uncertainty as each claim's confidence, (d) a false premise of the lens in `risks`, and at most ONE claim starting "Outside my lens:"; "nothing significant" and "cannot establish" are findings; its `recommendation` may be null, as for every member now; `lensOnlyMemberSchema` changes only an older stored schema that still required an object. A member left without a lens (the planner gave fewer, none, or failed) answers the question as asked, with the usual prompt and schema, and the plan records it (`unassigned`, `planner.state`/`planner.error`); the round never fails for the planner. The chairman's input has, before each anonymous block, a line `Member X: assigned instruction: <lens>` or `Member X: no lens (anchor)` / `no lens: it answered the question as asked` (`lensLine`), and its rules (`lensChairmanRules`, in `session.settings.chairmanRules`) say: judge claims by support, relevance and consequence; confidence numbers and agreement counts are not evidence; a hypothetical concern is not factual dissent; keep a supported minority point; never trust a lens answer because it sounds relevant. In `only` the chairman alone answers the asker, from the findings (evidence to assess, not conclusions; the lenses are prompts, not expertise; an area no finding covers stays unknown; it alone weighs the trade-offs and recommends), and `agreement.of` is its own count of the findings that bear on the recommendation (at most the members it was given; null when 0 or when it gives none). **Stored on the round (`ChairNode`)**: `lensMode`, `lensPlan` (`mode`, `requested`, `lenses`, `anchorSeatId`, `assignment` by seat id, `unassigned`, and `planner`: `state`, `harness`, `model`, `error`, `usage`, `trimmed`, times), and on each `SeatRun` `lens` (a `{question, why}`, `"anchor"`, or `null`). The planner's call is an attempt of kind `planner` (label `planner`) and its tokens are `usage.planner`, counted in `usage.total` (so in the meter). **Provisional:** lenses work on the FIRST round only; a later round (a follow-up, a branch) is an ordinary round (no `lensMode`, no lens), and a round run again plans again (its second planner call is one more attempt). The fake planner (`DIVAN_FAKE=1`) returns deterministic lenses (`FAKE_LENSES`); a chairman model named `fake-lens-few`, `-none`, `-fail` or `-bad` gives it a bad day.
